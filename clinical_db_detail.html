Project Overview

This project tackled the challenge of extracting clinically relevant data from an undocumented PostgreSQL database with complex nested JSON structures to make it available for researchers. A pair of advanced SQL functions prompting the keyword(s) related to the searched results enabled the efficient search for the clinically relevant data.

🎯 Key Innovation

The Challenge: The PostgreSQL database, containing critical clinical research data across 30+ tables with complex nested JSON objects was completely undocumented. Researchers knew the keywords to extract the relevant data, but had no idea where in the complex nested JSON structures it was stored. Running a simple script across all the records a specific patient searching for a specific keyword took several hours.

The Solution: Rather than manually exploring 30+ tables, we implemented a recursive solution with the help of 2 advanced PostgreSQL functions performing automated discovery—scanning all records of a certain patient, traversing unknown JSON hierarchies, and revealing:
  • WHO has the data (patient/case identifiers)
  • WHERE it's located (complete JSON key paths)
This transforms an undocumented database into a fully searchable and queryable research resource, with the JSON paths serving as a schema map for future data extraction.

💻 Two-Function Architecture

The solution consists of two PostgreSQL functions working together in a recursive workflow to discover which patients have matching data and where in the JSON structure it's located—returning a three-part result: patient number (patnr), case number (fallnr), and JSON key path.

1️⃣ Main Wrapper: find_jsonb_string_path

Scans all records in the database table, calls the recursive function on the JSONB column with the clinically relevant data, and returns a three-part tuple for every match: (patient_id, case_id, json_path). 

CREATE OR REPLACE FUNCTION find_jsonb_string_path(
    table_label TEXT,      -- Table to search
    search_string TEXT     -- String to find
) RETURNS TABLE(
    patnr TEXT,           -- Patient number (Patientennummer)
    fallnr TEXT,          -- Case number (Fallnummer)
    path TEXT             -- JSON key path where data was found
) LANGUAGE plpgsql AS $$
DECLARE
    rec RECORD;
    json_path TEXT;
BEGIN
    -- Scan through all records in the specified table
    FOR rec IN
        EXECUTE format(
            'SELECT t.patnr, t.fallnr, t.content FROM %s t',
            table_label
        )
    LOOP
        BEGIN
            -- Call recursive function to search within JSON
            json_path := find_in_jsonb(rec.content, search_string, '');

            IF json_path IS NOT NULL THEN
                -- Match found! Return the three-part tuple:
                RETURN QUERY SELECT
                    rec.patnr::TEXT,    -- 1. Which patient
                    rec.fallnr::TEXT,   -- 2. Which case
                    json_path::TEXT;    -- 3. Where in the JSON
            END IF;
        END;
    END LOOP;
END;
$$;

2️⃣ Recursive Core: find_in_jsonb

Recursively traverses JSON objects and arrays of unknown structure, building the key path as it searches for matching strings within the complex JSON structure of objects stored in the "content" column and returning the complete path when found a match. 

CREATE OR REPLACE FUNCTION find_in_jsonb(
    json_value JSONB,
    search_string TEXT,
    current_path TEXT
) RETURNS TEXT AS $$
BEGIN
    -- Handle JSON objects
    IF jsonb_typeof(json_value) = 'object' THEN
        FOR key, val IN SELECT * FROM jsonb_each(json_value) LOOP
            result := find_in_jsonb(val, search_string, current_path || '.' || key);
            IF result IS NOT NULL THEN RETURN result; END IF;
        END LOOP;

    -- Handle JSON arrays
    ELSIF jsonb_typeof(json_value) = 'array' THEN
        FOR idx IN 0..(jsonb_array_length(json_value) - 1) LOOP
            result := find_in_jsonb(json_value->idx, search_string, current_path || '[' || idx || ']');
            IF result IS NOT NULL THEN RETURN result; END IF;
        END LOOP;

    -- Handle strings (actual comparison)
    ELSIF jsonb_typeof(json_value) = 'string' THEN
        IF json_value::TEXT ILIKE '%' || search_string || '%' THEN
            RETURN current_path;
        END IF;
    END IF;

    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

🔄 How They Work Together

  1. Physician's question: Example: "Which patients have mechanical ventilation documented?"
  2. Main function scans through all records, extracting JSONB columns.
  3. For each record, the recursive function traverses the "content" column (of JSON type):
    • Objects → recurse into key-value pairs, building paths like .procedures.ventilation
    • Arrays → recurse into elements, building paths like .items[0].name
    • Strings → compare with search term
  4. When match found: Returns (patnr, fallnr, path) tuple.
  5. Result: Complete list of all matching patients with precise data locations.

📝 Example: Three-Part Output

-- Search across all patients in ICU procedures table
SELECT * FROM find_jsonb_string_path(
    'ukbb.icu_procedures',
    'ventilation'
) LIMIT 5;

-- Returns three-part tuples:
-- patnr   | fallnr  | path
-- 412541  | 5193452 | .procedures.respiratory.ventilation.mode
-- 387629  | 5201103 | .interventions.ventilation.settings
-- 401258  | 5189773 | .care_plan[0].ventilation_protocol

The Three Essential Pieces

  1. patnr (Patientennummer): Identifies WHICH patient has the data.
  2. fallnr (Fallnummer): Identifies WHICH specific case or admission.
  3. path: Reveals WHERE in the JSON structure the data is stored.

With this three-part output, researchers can immediately identify patient cohorts AND know how to extract the relevant data. For example, knowing the path .procedures.respiratory.ventilation.mode enables writing queries like: 

SELECT
    patnr,
    content->'procedures'->'respiratory'->'ventilation'->>'mode' AS vent_mode
FROM ukbb.icu_procedures
WHERE patnr IN (412541, 387629, 401258);

Key Technical Features

  • Recursive Algorithm: Handles arbitrary JSON nesting depth.
  • Type-Safe Traversal: Correctly handles objects, arrays, strings, numbers, booleans, and nulls.
  • Dynamic SQL: Parameterized queries prevent SQL injection.
  • Path Construction: Builds readable JSON paths (e.g., .procedures[0].ventilation.mode)
  • Pattern Matching: Uses ILIKE for flexible, case-insensitive searching.
  • Error Handling: Gracefully skips problematic records to continue discovery.
